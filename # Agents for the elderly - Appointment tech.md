1. Purpose and scope
This document specifies everything a developer needs to implement the Appointment Cycle feature of the Geriatric Care Agent. It covers data models, conversation flow triggers, business logic, output formats, bifurcation rules, non-negotiable constraints, and integration points with other system components.
The appointment cycle is the highest-priority MVP feature. It is the primary entry point through which informal caregivers of people with dementia will first experience the agent's value. It must work end-to-end before any other feature is built.

Design principle: Practical capture creates the psychological substrate. Every conversation in this feature serves both an administrative and a relational function. The agent holds both at once; it never delegates one to the other.

1.1 What this feature does
The appointment cycle supports the caregiver through three phases of every specialist or GP appointment involving the person with dementia:
•	Phase B1 (Pre-appointment, 48–72 hrs before): Observation harvest, question prioritisation, and clinical brief generation.
•	Phase B2 (Day of appointment): Morning brief delivery, advocacy coaching, and immediate post-appointment voice/text capture.
•	Phase B3 (Same day or next day): Structured clinical debrief, family update draft, and emotional debrief with psychological integration.

1.2 What this feature does not do
The following are hard constraints, not soft guidelines. Any implementation that touches these areas must be rejected:
•	The agent does not transmit any document, message, or data to any clinician, health system, or electronic health record.
•	The agent does not create, read, modify, or delete records in any external clinical system.
•	The agent does not provide clinical advice, interpret test results, or make diagnostic suggestions.
•	The agent does not send appointment reminders to anyone other than the caregiver.
•	The employer reporting layer has zero access to any appointment content. It receives only anonymised, aggregate appointment frequency counts.

 
2. Data model
2.1 Appointment record
Each appointment creates a single, versioned appointment record linked to the caregiver's longitudinal situation model. All fields are caregiver-owned and caregiver-controlled.

Field	Type	Description
appointment_id	UUID	Primary key, unique per appointment
caregiver_id	UUID	FK to caregiver profile
situation_model_id	UUID	FK to longitudinal situation model
appointment_date	ISO 8601	Date and estimated time of appointment
appointment_type	ENUM	gp | neurologist | memory_clinic | geriatrician | other
elder_name	String	Display name for elder (from situation model)
clinician_name	String	Optional, caregiver-provided
caregiver_type	ENUM	cohabiting | distance — from situation model
observations	Object	Structured observations by domain — see 2.2
question_list	Array[max 5]	Ranked question objects — see 2.3
clinical_brief	Object	Generated brief — see 2.4
b2_morning_sent_at	Timestamp	When the day-of brief was delivered
b2_voice_capture_raw	Text	Raw transcription of post-appt voice/text capture
b3_debrief	Object	Post-appt decisions and follow-up — see 2.5
family_update_draft	Text	Draft family update, caregiver-approved flag
burden_signal_triggered	Boolean	True if D5 passive detection triggered during any phase
created_at	Timestamp	Record creation
updated_at	Timestamp	Last update
version	Integer	Optimistic locking counter

2.2 Observations object
Observations are structured by clinical domain. Each domain contains free-text notes captured conversationally by the agent, plus a caregiver-rated change indicator.

Domain	What the agent captures
cognitive	Memory, orientation, language, recognition episodes, confusion patterns
bpsd	Behavioural and psychological symptoms: agitation, wandering, sleep, paranoia, repetitive behaviour
adl	Independence in activities of daily living: bathing, dressing, eating, mobility, toileting
physical	Physical health changes relevant to dementia: weight, appetite, falls, pain, medication side effects
medication	Current medications, recent changes, adherence issues, suspected interactions, caregiver uncertainties

Each domain also stores:
•	change_since_last_appt: ENUM (improved | stable | worsened | new_symptom)
•	linked_incident_ids: Array[UUID] — incident log entries referenced during harvest
•	caregiver_notes: Free text, verbatim from conversation before structuring

2.3 Question list object
Maximum five questions, stored as an ordered array. Each question object:

{ question_id: UUID, rank: 1-5, raw_text: String (caregiver's own words), structured_text: String (agent-translated clinical language), approved_by_caregiver: Boolean, asked_in_appointment: Boolean | null, answered: Boolean | null }

2.4 Clinical brief object
The clinical brief is a caregiver-owned document generated by the agent and approved before any use. It has four named sections:
•	current_status: 2–3 sentence summary of the elder's current condition and stage.
•	changes_since_last_appointment: Domain-structured observations (from 2.2), date-stamped where available.
•	questions: The approved question list in ranked order (structured text).
•	medication_list: Current medications with any flagged changes, confusions, or suspected issues.

Additional fields:
•	generated_at: Timestamp
•	caregiver_approved: Boolean — brief cannot be presented or used until true
•	share_log: Array of {shared_with, method, timestamp} — populated if caregiver shares externally

Implementation note: The agent generates the brief text; the caregiver reads and approves it conversationally. Do not build a separate 'brief editor' UI. Approval happens in the conversation: the agent presents sections, the caregiver confirms or amends.

2.5 Post-appointment debrief object

Field	Description
decisions_made	Free text: what was clinically decided (medication change, referral, staging update, etc.)
follow_up_items	Array of { task, owner, due_by } — e.g. book blood test, collect prescription
next_appointment_date	ISO 8601, optional
family_update_approved	Boolean — caregiver has approved the draft family update
emotional_debrief_opened	Boolean — whether the caregiver engaged with the emotional debrief prompt
emotional_debrief_notes	Summary of emotional content if engaged — used only for D5 signal, never shared
psychological_domains_activated	Array[ENUM] — D1 | D2 | D5 | D6 — which domains were engaged

 
3. Conversation flows
3.1 Phase B1 — pre-appointment preparation
Trigger conditions
The B1 conversation initiates automatically when all of the following are true:
1.	An appointment record exists with appointment_date set.
2.	Current time is between 72 and 48 hours before appointment_date.
3.	B1 has not already been completed for this appointment_id (no approved clinical_brief exists).
4.	The caregiver has not explicitly deferred B1 for this appointment.

Implementation note: Do not trigger B1 if the caregiver is mid-conversation on another topic. Queue and deliver at the next natural opening or at a scheduled check-in time.

Conversation stages
B1 has five sequential stages. The caregiver may pause and resume between stages. State is persisted after each stage.

#	Stage	Agent behaviour
1	Warm open	Reference the elder by name and appointment type. Ask how the elder has been since last time. Do not ask for symptoms directly. Elicit narrative first.
2	Observation harvest	Work through the five observation domains conversationally. Surface relevant entries from the incident log and previous check-in notes. Prompt by domain only if the caregiver has not naturally covered it. Do not ask all five sequentially — follow the caregiver's account.
3	Question generation	Reflect observations back as candidate questions. Limit to five. Ask the caregiver to rank them. Translate caregiver language into clinical language for the brief, preserving intent. Show the translation and ask for confirmation.
4	Brief generation	Generate the clinical brief section by section. Present each section to the caregiver for review. Amend on request. Set caregiver_approved = true only after explicit confirmation of all four sections.
5	Anxiety acknowledgement	After brief is approved, offer a psychological check-in: 'Is there something specific you are worried they might say?' Do not force engagement. If the caregiver declines, close B1 gracefully.

Bifurcation: cohabiting vs. distance caregiver
Read caregiver_type from the situation model before B1 initiates.

Stage	Cohabiting	Distance
Warm open	Ask about logistics: getting there, who stays with the elder.	Ask about how much context they have from day-to-day. Surface cohabiting carer notes if available.
Observation harvest	Draw from full incident log and check-in record.	Supplement with any notes from cohabiting carer (if flagged in situation model). Flag gaps in observation explicitly.
Anxiety acknowledgement	Focus on elder's likely distress during appointment (clinical visit effect).	Acknowledge guilt about not being present more. Reframe: 'You know more about the situation than you may realise.'

Dementia-specific logic in B1
The following logic applies only when appointment_type is neurologist, memory_clinic, or geriatrician and the condition in the situation model includes dementia:
•	Surface the ‘clinical visit effect’ psychoeducation: people with dementia often perform better in clinic than at home. Prepare the caregiver to name this to the clinician.
•	If MMSE or CDR score exists from a previous appointment record, reference it contextually: 'Last time the score was X — scores often vary, and the clinician will want to know what you’ve been seeing at home.'
•	If the incident log contains BPSD entries (agitation, wandering, paranoia), flag these explicitly for the brief. These are high-value clinical observations that caregivers frequently fail to report.

3.2 Phase B2 — in-appointment support
Trigger: morning brief
On the morning of appointment_date (default 07:30 caregiver local time, configurable), deliver a short morning brief. This is a single push notification or in-app message, not a conversation initiator.
Morning brief contains:
•	Top 3 questions from the approved question list (ranked 1–3).
•	A reminder that the clinical brief is ready.
•	One advocacy coaching note — chosen from the coaching library based on appointment_type and caregiver_type (see 3.2.1).
•	For distance caregivers: a brief context summary sentence ('You last attended an appointment in [month]. Here is what has changed since.').

3.2.1 Advocacy coaching library
The coaching library contains short, appointment-type-appropriate scripts. The agent selects one per appointment. Examples:

Context	Coaching note
General	'You can introduce yourself at the start and say: I'm the primary carer — I want to make sure I understand what is decided today and I have a few questions. That sets the expectation that you are there as a partner, not just an observer.'
Dementia, performance gap	'It is common for people with dementia to seem sharper in clinic than at home. If this happens, you can say: She is often much more confused at home — I have some specific examples I’d like to share.'
Memory clinic / MMSE	'If the score has changed since last time, the clinician will explain why. Scores fluctuate. The number is only one part of the picture — your observations matter equally.'
Distance caregiver	'You have been following this situation closely from a distance. You are allowed to ask for the full picture, not just the summary.'

Trigger: post-appointment capture
30–60 minutes after the appointment end time (estimated from appointment_date and typical appointment duration by type), the agent sends a single prompt:

"How did it go? Tell me while it's fresh — even just a few sentences."

The caregiver may respond by text or voice note. Voice notes are transcribed server-side before storage. The raw response is stored in b2_voice_capture_raw. The agent does not attempt to structure the response at this stage — that happens in B3.

Edge case: If no response is received within 4 hours of the capture prompt, the agent sends one follow-up: 'Whenever you're ready — I'll be here.' No further prompts are sent. B3 can still be initiated by caregiver message at any time.

3.3 Phase B3 — post-appointment debrief
Trigger conditions
B3 initiates when any of the following occur:
5.	b2_voice_capture_raw is populated (automatic, after a short processing delay of 15 minutes).
6.	The caregiver sends a message that conversationally references the appointment (e.g. 'just got back from the doctor').
7.	The caregiver explicitly asks to start the debrief.

Debrief sequence
The debrief sequence is fixed. Practical comes before emotional. This order must not be reversed.

Step	Stage	Agent behaviour
1	Structure B2 capture	Parse b2_voice_capture_raw and extract: decisions made, follow-up items, next appointment date, and anything clinically notable. Store in b3_debrief.decisions_made.
2	Confirm and correct	Present the structured summary to the caregiver. 'Here is what I've captured from what you said — is there anything I've missed or that needs correcting?'
3	Follow-up items	For each follow-up item identified, establish: task, owner (caregiver, GP, specialist), and due date. Store in b3_debrief.follow_up_items. These will reappear as reminders.
4	Family update	Generate a draft family update from the appointment record and debrief. Present it. 'Would you like me to draft an update for your brother and sister so you don't have to re-explain this three times?' Do not send until explicitly approved.
5	Emotional debrief	After step 4, offer a transition: 'Before we close this — how are you doing after all of that?' Do not skip this step. Do not force engagement. If declined, close gracefully.

Psychological domain activation in B3
The following rules govern which psychological domain modules are activated during the emotional debrief. These are not sequential — the agent detects signals and responds to whichever is most salient.

Signal	Domain	Agent response type
Confirmation of disease progression	D2 (grief)	Validate the ambiguous loss. Name both what remains and what has changed. Do not immediately offer coping strategies.
Caregiver doubts their advocacy ('I forgot to ask about driving')	D6 (self-compassion)	Evidence-based reappraisal using the appointment record: name what was asked and what was achieved. Frame the missed question as the top priority for next time.
Clinician dismissed or ignored the caregiver	D1 (validation)	Name the invisibility directly. Validate the caregiver's expertise as the primary observer. Do not coach on how to handle the clinician differently at this point.
Acute distress, hopelessness, 'I can't do this'	D5 (burnout)	Activate D5 passive detection enhancement. Follow escalation protocol. Set burden_signal_triggered = true.
Distance caregiver guilt about not attending more	D6 (self-compassion)	Reframe absence as circumstance, not abandonment. Name the effort of attending this appointment specifically.

 
4. Outputs generated by the appointment cycle
4.1 Clinical brief (B1 output)
Format: Structured text, four sections. Rendered in-app as a readable document. Printable. Shareable by caregiver via standard OS share sheet (PDF or plain text). The agent never shares this document independently.
Stored in: appointment_record.clinical_brief.
Used in: B2 morning brief (reference), B3 debrief (context), next B1 cycle (previous appointment reference).

4.2 Appointment record (longitudinal)
Stored in: appointment_record table, linked to situation_model_id.
Used in: next B1 (surfaces previous observations, previous questions asked), incident log cross-reference, D5 burden signal tracking.
Retention: indefinite, caregiver-owned. Caregiver can view full appointment history at any time.

4.3 Family update draft (B3 output)
Format: Plain text, 3–5 sentences. Human tone, not clinical. Caregiver-approved before any use.
Stored in: appointment_record.family_update_draft.
Shared only by: caregiver, via OS share sheet. The agent never sends this on the caregiver's behalf without explicit approval per instance.

4.4 Follow-up checklist (B3 output)
Format: Array of structured task objects stored in b3_debrief.follow_up_items. Each item has: task description, owner (caregiver | clinician | other), and due_by date.
Used in: reminder system. Follow-up items reappear in the caregiver's check-in at appropriate intervals. Items owned by clinicians are tracked but not actioned by the agent.

4.5 Burden signal (D5 integration)
If burden_signal_triggered = true during any phase, the D5 passive detection layer receives an enhanced signal. The appointment cycle does not handle escalation itself. It notifies D5 and passes context.
Context passed to D5: appointment_id, phase in which signal was triggered, emotional_debrief_notes summary (de-identified), current escalation level.

4.6 Employer reporting (aggregate only)
The employer reporting layer (Phase 6) receives only:
•	appointment_count: Number of appointments recorded per caregiver cohort per quarter. No individual-level data.
•	appointment_type_distribution: Aggregate breakdown of appointment types across the cohort. No individual-level data.
The employer layer has no access to: clinical brief content, observation notes, question lists, debrief content, emotional debrief notes, family update drafts, or any conversational content.

 
5. Integration with other system components
Component	Direction	What the appointment cycle reads or writes
Situation model	Reads	caregiver_type (cohabiting | distance), elder name, condition (dementia flag), previous MMSE / CDR scores, cohabiting carer notes if flagged.
Incident log	Reads	BPSD, ADL, cognitive, and physical entries since the last appointment. Used to surface observations the caregiver may have forgotten.
Medication record	Reads	Current medication list, flagged changes, adherence notes. Populates the medication section of the clinical brief.
D5 (Burnout detection)	Writes	burden_signal_triggered flag + context object. D5 decides escalation level; appointment cycle does not.
D1 (Validation)	Activates	D1 conversation patterns activate within the appointment cycle at pre-appointment anxiety, clinician invisibility, and emotional debrief moments.
D2 (Grief)	Activates	D2 patterns activate in B3 when progression is confirmed or disease stage changes.
D6 (Self-compassion)	Activates	D6 reappraisal patterns activate in B3 when caregiver expresses guilt about advocacy or attendance.
Reminder system	Writes	Follow-up items from b3_debrief.follow_up_items are registered as reminders with due dates.
Employer reporting	Writes (aggregate)	appointment_count and appointment_type_distribution only. No individual data.

 
6. Non-negotiable constraints
The following constraints must be enforced at the implementation level, not by policy. They are not to be revisited without explicit sign-off from the product owner and a clinical advisor.

Constraint	Implementation requirement
No clinical data transmission	The system must have no API connections to any EHR, EMR, or clinical information system. No outbound data to clinical endpoints.
No agent-initiated sharing	The clinical brief and family update draft are never transmitted by the agent. Sharing is exclusively through OS-level share sheet initiated by the caregiver.
Caregiver approval required	clinical_brief.caregiver_approved must be true before the brief is referenced in any output. family_update_approved must be true before the draft is surfaced for sharing.
Employer data isolation	The employer reporting query layer must be technically isolated from appointment record content. Enforce at the database access layer, not only by application logic.
Debrief sequence is fixed	The B3 practical debrief always precedes the emotional debrief. This sequence must not be alterable by configuration or by caregiver preference settings.
Escalation is D5-owned	The appointment cycle sets burden_signal_triggered and passes context. It does not implement escalation logic itself. D5 owns all escalation decisions.
Maximum five questions	The question list array enforces a maximum of five items at the data model level. The UI must reflect this constraint clearly.
No clinical interpretation	The agent never interprets test results, explains diagnoses, or suggests medication changes. It can ask the caregiver what the clinician said, and it can reflect that back, but it never adds clinical interpretation.

 
7. Edge cases and handling
Edge case	Expected behaviour
Caregiver does not complete B1 before appointment	On the morning of the appointment (B2 trigger), if no clinical brief exists, deliver an abbreviated morning brief with just the observation summary and an encouragement to note the top 2 questions.
No post-appointment capture received	After the 4-hour window, send one follow-up prompt. If still no response within 24 hours, send a gentle B3 opener: 'How did the appointment go whenever you're ready to talk about it.' Do not send further prompts.
Appointment cancelled or rescheduled	If caregiver indicates cancellation, archive the current B1 record (do not delete — observations remain valuable). Update appointment_date and restart the 72-hour B1 trigger for the new date.
Multiple appointments close together	If two appointments fall within 5 days, treat as separate appointment cycles. Do not merge records. Brief note in B1 warm open: 'You also have the [other appointment] coming up — we can cover that separately.'
Caregiver is very distressed before B1 completes	If D5 signal detected during any B1 stage, pause B1, follow D5 protocol. Resume B1 in a subsequent session if the appointment has not yet occurred. Do not force B1 completion during a crisis.
Elder refused to attend appointment	Capture refusal as a clinical observation. Offer to generate a brief summary for the GP of the refusal and the elder's current presentation at home. This is a high-value distress moment — open D1 (validation) immediately.
Distance caregiver did not attend the appointment	Acknowledge this without judgment. Ask if someone else attended. If yes, prompt the caregiver to relay the key information so the record can be updated. If no one attended, acknowledge the difficulty and focus on what the GP letter or discharge summary says.
Clinician communicated bad news (e.g. progression to severe stage)	D2 and D5 both get enhanced signals. B3 sequence is followed but emotional debrief is opened more explicitly: 'Before we do anything practical — how are you doing?' Practical debrief can follow after.

 
8. Open design questions for developer scoping
The following questions are not resolved in this specification. They require developer input before implementation begins.

•	Voice note transcription: Server-side or on-device? What latency is acceptable before B3 can be initiated after B2 capture? What language models or APIs are appropriate?
•	B2 timing: The 30–60 minute post-appointment window is estimated. Does the developer have access to a caregiver calendar or appointment system, or does the agent rely entirely on the caregiver-provided appointment time?
•	Notification delivery: The morning brief and post-appointment prompt require push notification capability. What notification infrastructure is available in the Claude Code build environment?
•	Clinical brief rendering: Should the brief be rendered as a formatted in-app view, a downloadable PDF, or plain text? PDF generation adds complexity; plain text is more accessible.
•	Conversation state persistence: How is B1 stage state persisted if the caregiver closes the app mid-preparation? What is the resumption behaviour?
•	Incident log access: The appointment cycle reads from the incident log domain (Domain C). If Domain C is not yet built, what stub data structure should the appointment cycle assume?
•	MMSE / CDR score storage: These scores may come from previous appointment records or from the caregiver's manual input. Where are they stored in the situation model, and in what format?

 
9. Acceptance criteria
The appointment cycle feature is considered shippable when all of the following pass:

Functional
•	B1 initiates automatically within a 10-minute window of the 72-hour pre-appointment trigger.
•	All five observation domains can be harvested conversationally without the caregiver completing a form.
•	The question list enforces a maximum of five items at the data model level.
•	The clinical brief is not surfaced in any context before caregiver_approved = true.
•	B2 morning brief delivers the top 3 questions and an advocacy coaching note.
•	B2 post-appointment prompt fires within the correct window after the appointment end time.
•	B3 practical debrief always precedes the emotional debrief, with no configuration option to reverse this.
•	The family update draft is not shareable until family_update_approved = true.
•	burden_signal_triggered correctly propagates to D5 with full context when activated.
•	No outbound connection exists to any clinical or EHR system.

Data isolation
•	Employer reporting query returns only appointment_count and appointment_type_distribution — no other fields.
•	A database access audit confirms the employer reporting layer cannot access appointment content fields.

Bifurcation
•	Cohabiting caregiver path includes logistics prompts in B1 and elder anxiety preparation in B2.
•	Distance caregiver path includes context-building from situation model and guilt reframe in B1.
•	Dementia-specific logic (clinical visit effect, BPSD flagging) activates correctly when condition = dementia.

Edge cases
•	All eight edge cases in Section 7 are handled without the agent crashing or producing an empty response.
•	Caregiver mid-B1 distress correctly pauses B1 and activates D5.

Clinical boundary
•	Agent produces no clinical interpretation in any phase.
•	Agent produces no diagnostic suggestions in any phase.
•	Onboarding disclosure of clinical boundary is visible and confirmed before first appointment cycle run.
